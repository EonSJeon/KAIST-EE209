# 과제 3 원본 리뷰

## 판단과 요구사항

PDF 제목은 **Customer Management Table**이다. 배열 구현의 `UserInfo`/`DB`와 해시 구현의 ID·이름 두 인덱스 및 네 연결 포인터를 유지했다. 핵심 문제는 자료구조 선택이 아니라 **여러 필드에 걸친 불변식과 자원 소유권**이다. 보관본에는 두 구현이 포함하는 `customer_manager.h`가 없어서 PDF의 공개 함수 선언으로 복원했다.

## 배열 구현의 오류

| 위치 | 실패 원인과 영향 | 고친 방법 |
|---|---|---|
| 직접 `pArray = realloc(...)` | 실패하면 여전히 유효한 옛 포인터를 잃고 DB가 망가진다. | 임시 포인터로 성공 확인 후 반영 |
| 확장된 구간 | `realloc`은 추가 메모리를 0으로 초기화하지 않는다. 새 슬롯의 임의 포인터를 읽을 수 있다. | 새 1024개 슬롯을 `memset` |
| 삭제 | name만 NULL로 만들고 id는 해제된 주소로 남긴다. 재등록 시 중복 검사에서 use-after-free가 가능하다. | 두 포인터를 NULL, 원소 수 감소 |
| `numItems` | 삭제 후 줄지 않아 빈 슬롯이 있어도 확장한다. | 실제 등록 개수와 일치 |
| 문자열 복사 | `strdup` 실패 후 부분 데이터가 들어가거나 메모리가 남는다. | 두 복사 성공 후 저장, 실패 시 rollback |
| 등록 순서 | 중복 거절 전에 용량부터 바꾼다. | 중복/빈 슬롯 확인 → 자원 확보 → commit |

## 해시 구현의 오류

두 인덱스는 **같은 노드를 가리키지만 서로 다른 체인**이다. 한쪽에서 노드를 지우면 다른 쪽의 head/prev/next도 함께 맞아야 한다.

- 새 노드의 `pastUbyid`/`pastUbyname`이 초기화되지 않았다. head 삭제 시 임의 주소를 이전 노드로 사용할 수 있다.
- 확장은 버킷 포인터를 `memmove`했을 뿐이다. 검색은 여러 과거 크기를 훑고, 삭제는 현재 크기로 다른 인덱스의 버킷을 계산한다. 실제 저장 위치와 계산 위치가 달라져 잘못된 head를 지우거나 해제된 노드를 남길 수 있다.
- 함수 `static incArr`는 DB별 상태가 아니다. 여러 DB를 만들면 서로의 확장 횟수에 영향을 준다.
- 삭제가 `nodeNum`을 줄이지 않는다.
- 생성·노드·문자열·확장 배열의 할당 실패를 점검하지 않는다.
- 파괴 시 노드의 문자열과 두 버킷 배열이 남는다.

수정본은 할당이 모두 성공한 새 배열에 **모든 노드를 현재 크기의 해시로 재배치**한다. 그 뒤에는 한 버킷만 조회한다. 75%에서 두 배 확장하고 2^20 버킷 상한을 유지한다. 실패 전까지 기존 데이터는 손대지 않는다.

## 이 코드에서 바꾸면 좋은 습관

`free()` 호출만 세지 말고 소유 포인터의 상태와 실제 원소 수도 함께 확인한다. 연결 리스트는 head/middle/tail/유일 노드 네 경우를 양쪽 인덱스에서 확인한다. 해시는 용량 변경 전후에 모든 키가 검색 가능해야 한다는 불변식을 먼저 적는다. 정상 메모리 환경의 테스트에 더해 N번째 할당이 실패하는 상황도 검사한다.

## corrected 검증

같은 클라이언트를 두 구현에 각각 링크한다. 4096건 등록·이름/ID 조회·중복 거절·양쪽 삭제·2048회 슬롯 재사용·서로 독립인 두 DB·문자열 복사·callback 호출 수를 확인한다. 별도 fault 빌드에서는 생성/등록/배열 확장/해시 확장 할당을 차례로 실패시키고, rollback과 남은 할당 0개를 확인한다. 실행 시간도 클라이언트가 출력하지만 수업 전체의 성능 순위를 뜻하지 않는다.

```sh
./run.sh
./run.sh --test
```

명령은 `corrected`에서 실행한다. `testclient.c`, 헤더, fault 테스트 도구는 이번 검토에서 추가한 파일이다.
